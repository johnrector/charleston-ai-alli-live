# Finite voicemail playback and hangup

The original call left its reminder, then continued listening to the mailbox menu. Closing a call depended on a later delegated Agent action. Primary GPT-Live streams do not expose a reliable output-audio-done boundary, so a transcript sentence, timestamp, silence gap or context acknowledgment cannot authorize hangup after actual playback.

The outbound voicemail path now has one finite message prepared before dialing, using the existing OpenAI speech API and configured Marin voice. Appointment text contains only the saved recipient name and bound calendar time/place; other missions use a generic callback message. Existing call-specific `hang_up` preference skips rendering and leaves no message. Failed or uncertain rendering holds the never-dialed call without a retry. Appointment holds appear in existing diagnostic coverage.

Twilio `DetectMessageEnd` runs asynchronously, leaving the human GPT-Live path connected immediately. A signed callback must match the saved call and provider identity. The signed machine_end_beep, machine_end_silence or machine_end_other verdict is the documented recording-ready signal. Human, unknown and fax do not start automatic voicemail. No transcript or second model request is required; delayed ASR text is not a speech/interruption clock. Live may supply no transcript at all. Raw inbound audio after readiness and signed human detection override automatic playback. No Decisions permission or new credential is requested.

Live listens for an actual human answer before the outbound mission greeting and remains silent over recorded greetings. The application sends the finite PCMU asset and a unique final Twilio mark. Only that uncleared mark's acknowledgment authorizes one carrier completion request. Clear, disconnect, stale/unknown marks and transport deadline do not count as played. The media-sized deadline is an acknowledgment failure bound; it never ends a silent call. Incoming audio/speech or human detection cancels playback/hangup, invalidates marks, and restores ordinary Live output. Playback and delegated-end reservations prevent races; actual end actions retain durable once-only receipts. An already-issued completion request continues independently of media teardown, with a ten-second transport deadline. An uncertain carrier result is never retried.

No research, rendering or provider acknowledgment is awaited in normal Live startup/audio handling. Optional voicemail initialization runs after `session.started`. Source freshness and existing appointment authorization checks run after speech preparation and immediately before dialing. Normal inbound calls retain their existing path. No separate scheduler, campaign, CRM database or new infrastructure is added.

## Evidence and limits

`ea_call_voicemail` stores one asset/attempt per existing call, source text/digest, detector state, playback state, hangup state and timestamps. Raw audio is owner-side storage, omitted from tools/dashboard and model context. Owner call lookup, diagnostic call page and mission context expose separate finite-message receipts. Generated Live transcript captured while application output is suppressed is labeled unverified, so it is not silently promoted to spoken dialogue. A carrier mark proves playback, not mailbox storage or attendance confirmation. After close, transport evidence stores packet/event counts and the exact acknowledged finite mark identity. No audio bytes or transcript content are copied into these counts. Historical calls have no retrospective transport counts.

If any Live audio has already been sent, the finite reminder is held to avoid duplicate or truncated speech; the ordinary delegated end remains available. Ambiguous detection or missing playback acknowledgment also holds automatic voicemail control. These are visible exception states, not success. Runtime voice rendering and signed AMD callback delivery were exercised by the single authorized owner test below; playback/hangup success, AMD accuracy across callers, noise handling and real-world timing remain unvalidated after this correction. Production provider refusal does not grant scopes or trigger a fallback/retry. Standard per-use speech/AMD charges may apply to future authorized calls; no subscription, service provisioning or probe is part of this change.

The migration is additive and idempotent: one table, a composite unique index for its scoped foreign key, and additive columns. Old calls are not replayed, re-rendered or backfilled. Old code can run with these unused additions left in place. Retain rows/receipts on rollback; do not drop historical evidence.

Verification uses isolated disposable Postgres and mocked provider APIs, covering finite byte ordering, clear/stale marks, interruption during lock/DB windows, zero/delayed transcript behavior, human recovery, signed callback identities, no-message preference, missing acknowledgment, rendering failure, completion continuing after media teardown, uncertain hangup, and once-only actual end requests. The initial repair used no live call. One subsequent owner voicemail test was explicitly authorized; its failure is recorded below. No second call, SMS or additional provider probe is authorized without fresh approval.

## Exact owner-authorized message and silent completion

For an explicit exact voicemail, the existing owner `call_outbound.approved_logistics` string accepts a JSON object containing only `voicemail_message` (1–800 characters, no control characters) and optional `completion_notification` (boolean). Message text is persisted separately and read verbatim, never inferred from mission prose. Plain logistics text retains its prior meaning. `completion_notification:false` places a server-enforced `notification_policy:none` on the owner call task and its new preparation/voice-child tasks; model output cannot re-enable completion SMS. Existing stable request identity includes the original logistics object; it cannot be used to change/replay a call. This does not grant calling, messaging or account authority.

## Single authorized real test and correction

One owner test on October 31 rendered the exact approved 6.35-second message and received a valid machine_end_beep callback. Live supplied zero transcript deltas. The extra transcript prerequisite in the first release prevented playback and hangup; the carrier eventually ended the call after 150 seconds. No message delivery is claimed. No SMS, email or redial was requested or performed.

The correction removes that unnecessary prerequisite and its Responses classifier. Signed DetectMessageEnd starts the existing once-only finite playback even with no transcript. Raw-audio activity during arming/playback, human detection, prior Live output, mark invalidation and no-retry guards remain. Tests reproduce zero-ASR readiness and delayed greeting transcripts rather than assuming ASR exists. The underlying reason Live supplied no transcript in that call is not established; transport input/forwarding/event counts will distinguish it on future authorized calls. A second call requires fresh approval.
